# Архитектура

## Общая схема

```
                ┌──────────────────────────────── backend (FastAPI) ────────────────────────────────┐
 data/real|synth│  sources.py        pipeline.py                                                     │
 RSS (4 шт.)  ──┼─> загрузка ──> normalize ──> extract (nlp.py) ──> SQLite events ──> recluster      │
 Альфа (нет)    │                                                       (dedup.py, TF-IDF)          │
                │                                                                                    │
                │  запрос /api/events?profile_id=…                                                   │
                │     analyze_all(profile):                                                          │
                │       matching.find_matches   — что из профиля есть в новости                     │
                │       analysis.detect_channels — каналы влияния (правила)                         │
                │       scoring.score_event     — релевантность / влияние / срочность / уверенность │
                │       analysis.build_insight  — разбор из 10 блоков + действия                    │
                │     кэш в памяти (профиль + версия данных + час)                                   │
                │                                                                                    │
                │  /api/events/{id}/llm  ──> llm.py (разрешённая LLM, JSON-схема) ──> verify         │
                │  /api/agent/insight    ──> agent.py: план -> инструменты -> самопроверка -> 6 ответов │
                │                            кэш в таблице analyses                                  │
                └────────────────────────────────────────────────────────────────────────────────────┘
                                   │ JSON
                ┌──────────────── frontend (React + Vite + Tailwind) ─────────────────┐
                │ Обзор · Лента · Событие · Профиль · Решения                          │
                └──────────────────────────────────────────────────────────────────────┘
```

## Почему так

- **Анализ считается на лету** для выбранного профиля. Демо-набор — десятки событий, живой RSS — 100–200,
  на ноутбуке это доли секунды. Плюс: правка профиля сразу меняет все оценки, ничего не нужно пересчитывать в БД.
- **LLM не принимает решений.** Отбор, ранжирование и баллы делают правила. LLM только переписывает разбор
  по схеме и вызывается по кнопке. Так система предсказуема, работает без ключа и не тратит деньги на шум.
- **SQLite + sqlite3** без ORM — для MVP хватает, ноль настроек.

## Конвейер

1. **Получение** (`sources.py`). Встроенный набор выбирается `DATASET`: `real` — подборка реальных публикаций
   (настоящие даты, ссылка, пересказ фактов), `synthetic` — вымышленные события с датами от «сейчас».
   При каждом запуске набор синхронизируется с файлом, признаки всех событий пересчитываются. RSS — `httpx` + `feedparser`, таймаут,
   не больше `RSS_RETRIES` повторов и только при сетевых ошибках или 5xx. Ошибки пишутся в `fetch_log`.
2. **Нормализация** (`pipeline.normalize`). Пробелы, пустой анонс, даты в UTC, хэш заголовка для дублей.
3. **Извлечение** (`nlp.py`). Токены и стемминг (Snowball), категория, регионы (словарь с корнями), отрасли,
   сигналы направления (`price_up`, `supply_disruption`, `regulation`, `rate_up`, `rub_strong`…),
   признак инструкций для ИИ, признак «спорт/культура».
4. **Дубли** (`dedup.py`). TF-IDF по стемам, косинус ≥ 0,3, окно 3 дня; если косинус < 0,6, в заголовке
   или анонсе должно совпасть хотя бы одно число (разные события на одну тему обычно расходятся в цифрах).
   Синтетика и реальные новости не смешиваются. В карточке — самый надёжный источник, остальные — «похожие публикации».
5. **Сопоставление с профилем** (`matching.py`). Компания ищется по названию и псевдонимам («Сбер» = «ПАО Сбербанк»).
   Строгое совпадение для имён и продуктов (все слова термина), частичное — для длинных формулировок целей и рисков.
   Поставщик «Субстанции (Индия)» даёт регион риска «Индия».
   Флаги профиля: основная отрасль, экспортёр, импортёр, долг с плавающей ставкой, банк.
6. **Каналы влияния** (`analysis.detect_channels`). Таблица правил «сигнал × что совпало в профиле»:

   | Сигнал в новости | Совпадение в профиле | Вывод |
   |---|---|---|
   | рост цен / тарифов | поставщики | риск: рост затрат |
   | снижение цен | поставщики, инвестпланы | возможность: дешевле закупки/капекс |
   | ограничения, задержки | поставщики или их регион | риск: срыв поставок |
   | ограничения на маршруте | экспортёр + продукты | риск: задержка отгрузок |
   | рост спроса | продукты, клиенты | возможность |
   | закон / требования | отрасль, продукты, приоритеты | риск: проверить применимость |
   | льготы, поддержка | отрасль, инвестпланы, продукты | возможность |
   | ключевая ставка ↑ | долг / инвестпланы | риск: дороже деньги |
   | укрепление рубля | экспортёр / импортёр | риск / возможность |
   | авария у конкурента | конкуренты | возможность: забрать долю |
   | расширение конкурента | конкуренты | риск |
   | снижение пошлин за рубежом | экспортёр + продукты | возможность: экспортная ниша |
   | ключевая ставка без изменений | долг / инвестпланы | риск: дорогие деньги дольше |
   | любое решение по ставке | банк | маржа, спрос на кредиты, качество портфеля |
   | спрос падает / растёт | только клиенты | дела у клиентов (для банка — у заёмщиков) |
   | снижение цен | продукты компании | риск: давление на выручку |
   | рост цен | риск затрат из реестра компании | реализуется риск из реестра |
   | ничего из перечисленного, но компания упомянута | — | новость о самой компании |

   Каждый канал содержит цепочку «событие → механизм → эффект», действия с ролью и сроком и индикаторы.
7. **Баллы** (`scoring.py`):
   - *релевантность* — сумма факторов: отрасль, продукты, регионы, контрагенты, стратегия, реестр рисков,
     ключевые слова, найденные каналы, «чувствительность из профиля», смысловая близость (TF-IDF);
     штраф за спорт/культуру;
   - *влияние* — масштаб события + наличие цифр + сила каналов, умноженные на связь с компанией;
   - *срочность* — свежесть, срок в тексте, идущий сбой, сильный канал;
   - *уверенность* — надёжность источника, число источников, объём текста, прямые упоминания,
     минус за подозрительный текст;
   - *приоритет* = 0,45·R + 0,25·I + 0,20·U + 0,10·N; при уверенности < 40 — минус 5;
     при релевантности < 25 приоритет не выше релевантности + 10.
8. **Разбор** (`analysis.build_insight`). Факты — только цитаты из текста источника (предложения с цифрами и датами).
   Отдельно — допущения и «чего не хватает».

## Справочники профиля (`catalog.py`)

- 13 отраслевых шаблонов: подотрасли, продукты, клиенты, поставщики, конкуренты, цели, приоритеты, риски, инвестпланы,
  ключевые слова. Формулировки подобраны так, чтобы их слова встречались в новостях: matching ищет термин по корням.
- `GET /api/profile-options?industry=` — варианты для каждого поля: `suggested` (шаблон отрасли) и `other` (общие,
  другие отрасли и всё, что пользователи уже вводили в профилях).
- `POST /api/profiles/suggest` — черновик профиля: первые значения шаблона + то, что нашлось в описании (все слова
  варианта должны быть в тексте; регион в обороте «из Китая» считается географией поставщиков, а не присутствия).
  Отрасль определяется по названию, а если она своя — по словарю отраслей в названии и описании.
- Новый профиль сохраняется с `autofilled: true`; при сохранении формы флаг снимается. Анализ всегда идёт по тому,
  что лежит в базе, то есть по версии пользователя.

## Своя модель (`model.py`)

- Метки двух видов: оценки пользователя (`feedback`, вес 1) и рыночная разметка (`auto_labels`, см. ниже).
  Если пользователь оценил событие, рыночная метка для него не используется.
- Пользователь оценивает разбор: относится ли событие к компании, тип влияния, верна ли важность (`feedback`).
- Вместе с оценкой сохраняется снимок признаков пары «событие — профиль»: баллы правил, факторы релевантности,
  совпадения с профилем, каналы, категория, сигналы, источник и слова заголовка в связке с отраслью компании
  (`metallurgy::порт`). Снимок, а не ссылка на событие — оценка остаётся валидной, даже если правила или профиль
  потом поменялись.
- После каждой оценки модель переобучается (миллисекунды): `DictVectorizer` + TF-IDF → `LogisticRegression`
  (`class_weight="balanced"`). Две модели: «значимо» (бинарная) и «тип влияния». Минимум 6 оценок и по 2 на класс.
  Модель общая для всех профилей. Хранится в таблице `models` (pickle), без файлов на диске.
- Качество — стратифицированная кросс-валидация до 5 фолдов против правил на тех же оценках (правила «значимо»,
  если релевантность ≥ 25).
- Применение (`pipeline.analyze_events`): сначала правила, затем `adjust_score` —
  `релевантность += вес × (100 × p − релевантность_правил)`,
  вес = min(0,5; 0,5 × n_польз / 20 + 0,25 × n_рынок / 60), вдвое меньше, если на кросс-валидации модель хуже правил.
  Модель типа влияния учится только на оценках людей. Поправка — отдельный
  фактор «Своя модель». Явная оценка события главнее модели: «не относится» → релевантность 5, «относится» → не
  ниже 50, «важность завышена/занижена» → ±15 к приоритету, тип влияния — как указал пользователь. Модель типа
  влияния подсказывает, только если правила не нашли канал (вероятность ≥ 0,6).
- Без контекста модели (`ml=None`) анализ — чистые правила: на этом построены тесты бизнес-логики.

## Поиск названий: морфология и NER (`ner.py`)

- При загрузке у события сохраняются леммы (pymorphy3) и организации/места (NER natasha, без персон).
- Название из профиля: аббревиатура (ПИК, НЛМК) — ищется заглавными; однозначное имя (Северсталь, X5) —
  совпадение лемм подряд; обычное слово или география («Магнит», «Лента», «Победа», «Россия») — только внутри
  организации, найденной NER. Какие термины считать названиями — `matching.is_name_term`; темы (продукты,
  ключевые слова, риски) ищутся по корням, как раньше.
- Без библиотек модуль отключается, поиск — по корням.

## Сюжеты (`threads.py`)

- Единица — группа дублей (dedup). Две группы связаны, если между ними ≤ 60 дней и: TF-IDF по леммам
  существительных и прилагательных ≥ 0,38; или ≥ 0,22 и общая редкая организация (NER) или два общих редких слова
  в заголовках. Union-find; в группах больше трёх оставляем события со средней похожестью ≥ 0,15.
- Название: общие слова в начальной форме, «прилагательное + существительное» согласуется («Ключевая ставка»),
  регистр — как в заголовках (МФО, Аэрофлот).
- Считается после каждой склейки (`pipeline.recluster`), хранится в `events.thread_id` и таблице `threads`.

## Готовый анализ и фоновый пересчёт (`store.py`, `jobs.py`)

- `pipeline.analyze_all`: память -> снимок в базе (`analysis_snapshots`, сжатый JSON) -> расчёт. Ключ снимка —
  отпечаток профиля, данных (новости, склейки, сюжеты), меток модели и кода. Снимок старше часа отдаётся сразу,
  пересчёт просится у фонового потока. Снимок пишется отдельным коротким соединением (таймаут 2 с).
- `jobs.py`: один поток, будится после загрузки ленты, правки профиля, изменения модели и раз в 10 минут проверяет
  устаревшие снимки. В тестах выключен (`ALPHA_BACKGROUND=0`).
- Портфель (`/api/portfolio`) и лента читают снимки — миллисекунды вместо секунд.

## Рыночная разметка (`market.py`)

Как учить модель без оценок пользователя: брать новости (в том числе старые) и смотреть, что было после них.
Для публичной компании «что было» измеряется реакцией акций.

- Котировки: Мосбиржа ISS (без ключа), дневные цены закрытия акций из профилей (`ticker`) и индекса IMOEX.
  Снимок `data/market/prices.json` загружается в таблицу `prices` при старте, кнопка «Обновить котировки» докачивает
  свежие дни.
- Окно реакции: день публикации (после 18:50 МСК — следующий торговый день) и следующий день.
  `AR = доходность акции − доходность индекса`, `z = AR / (σ × √2)`, σ — стандартное отклонение дневных AR за 60 дней.
- Метки: |z| ≥ 2 и релевантность по правилам ≥ 10 — «значимо» (вес 0,3; знак — риск / возможность);
  |z| < 0,7 и релевантность < 40 — «рынок не заметил» (вес 0,15); остальное не используется. Если у компании в один
  день реакции несколько размеченных новостей, вес делится на их число.
- Что размечается: события подборки и RSS из базы + `data/history/*.json` (только для обучения, в ленте их нет;
  дубли событий из базы пропускаются). Свежие новости ждут, пока закончится окно, и размечаются при следующем
  пересчёте (старт backend или кнопка в панели «Аналитика»).
- Почему не готовые датасеты (Kaggle и т.п.): там тональность новостей вообще, а не значимость для конкретной
  компании; архив можно подключить через `scripts/import_history.py` — он будет размечен рынком.
- Ограничения: шум (рынок двигают и другие события), только публичные компании (модель общая, поэтому знания
  переносятся на непубличные через признаки связи с профилем), «рынок не заметил» ≠ «бизнесу неважно».

## Компания из открытых источников (`lookup.collect`, `portals.py`, `company.py`)

1. ИНН -> ЕГРЮЛ (или DaData с ключом): название, регион, ОГРН.
2. Параллельно (ThreadPoolExecutor): Checko и «За честный бизнес» — публичные карточки по ОГРН (поиск на порталах
   закрыт robots.txt, карточки открыты); сайт компании — главная и до двух страниц из меню («О компании»,
   «Продукция»); Википедия — статья, в заголовке которой есть все слова названия и в тексте видно, что это
   организация.
3. Если сайт не указан, но найден на портале, — догружается.
4. `company.build`: отрасль голосованием, название в нормальном регистре, описание с фактами из реестров,
   подотрасли из родственных ОКВЭД (общие вроде «торговли через интернет» отбрасываются), продукты из структуры
   выручки, остальное — `catalog.suggest` по надёжным текстам и (строже) по тексту сайта.
5. Ответ содержит `sources_log` — что дал каждый источник; он же хранится в профиле (`autofill_info`).

robots.txt разбирается своим кодом по правилам Google (группа `*`, пустые строки внутри группы, `*` и `$`,
самое длинное правило). Ошибка любого источника не роняет остальные.

## Издания и достоверность (`outlets.py`, `data/outlets.json`)

- Реестр: название, шаблоны имени, страна, тип, репутация 0–1, холдинг. Агрегаторы проверяются первыми:
  «www1.ru (по данным ТАСС)» — перепечатка, а не ТАСС.
- Достоверность группы публикаций: репутация лучшего издания × 70 + независимые издания (по холдингам):
  2 — +12, 3 — +20, 4+ — +25 + официальный источник +15 − подозрительный текст 30. От 80 — высокая, 60–79 — средняя.
- Загрузка RSS (`pipeline.ingest_live`): 18 лент параллельно, российские — все новые, зарубежные — не больше 10%
  от новых (самые свежие), итог — в `settings.last_live`.

## Компания по ИНН и сайту (`lookup.py`)

- ИНН: контрольная сумма; при `DADATA_API_KEY` — DaData (есть ОКВЭД -> отраслевой шаблон), иначе публичный поиск
  ЕГРЮЛ на egrul.nalog.ru (название, регион, ОГРН, дата регистрации).
- Сайт: главная страница, `title`, `description`, `og:*`, заголовки и текст (без скриптов). Только http/https,
  все адреса после DNS и редиректов проверяются: внутренние сети запрещены; лимит 1,5 МБ и 10 секунд.
- Результат — в `catalog.suggest`: текст сайта ищется только по полям рынка (продукты, клиенты, регионы,
  подотрасли, ключевые слова), конкуренты и цели — только из описания пользователя. Ничего не сохраняется, пока
  фронтенд не создаст профиль (`autofilled: true`).

## LLM-слой (`llm_client.py`, `llm.py`)

- Только модели из приложения 3 кейса (Qwen3.6 35B A3B, GLM-5.3-Flash, Gemma 4 26B A4B, DeepSeek-V4.1-Flash,
  Kimi-K2.6, Qwen3-VL). Имя модели сверяется со списком до запроса, модель вне списка отклоняется.
- Протокол — HTTP Chat Completions через `httpx`; SDK OpenAI и Anthropic не используются. Провайдер `LLM_PROVIDER`:
  `gateway` (шлюз организаторов), `local` (своя модель: Ollama, vLLM), `off`.
- Роли: `fast` (Gemma — план агента), `reasoning` (GLM — ответ агента и разбор), `default` (Qwen).
- Каждый вызов — в таблице `llm_calls` (модель, назначение, токены, время, ошибка); дневной лимит токенов шлюза.
- Перед отправкой во внешний шлюз маскируются e-mail, телефоны, ИНН/ОГРН/КПП, номера счетов.
- Защита от инструкций в новостях:
  - текст новости — внутри `<news>…</news>`, угловые скобки экранируются, теги `news` вырезаются;
  - в системном промпте прямо сказано, что это данные, а не команды;
  - после ответа `verify()`: факты, которых нет в тексте (по пересечению стемов и цифрам), переносятся в допущения;
    уверенность не может быть выше, чем у правил, больше чем на 10; сроки действий ограничены 1–90 днями;
  - LLM ничего не исполняет: ответ — только данные для отображения.
- Ошибки (ключ, лимит, сеть, обрезанный ответ, отказ, невалидная схема) превращаются в понятное сообщение,
  интерфейс остаётся на анализе правил.

## Куда расширять

- Новый источник — функция, возвращающая список словарей того же формата, что `load_dataset_news()`, и вызов в
  `pipeline.ingest_live`.
- Новое правило — блок в `analysis.detect_channels` (+ при необходимости сигнал в `nlp.SIGNALS`)
  и строчка в `CHANNEL_ORDER`.
- Другой LLM-провайдер — отдельный модуль с функцией `analyze(ev, profile, rules_insight, score)`, возвращающей тот же
  словарь; `verify()` можно переиспользовать.


## Агент для ЛПР (`agent.py`)

Цикл на каждый запрос `POST /api/agent/insight {profile_id, event_id, question?}`:

1. **Планирование.** С LLM план строит разрешённая модель: получает реестр инструментов и сама выбирает, какие
   вызвать и с какими аргументами (JSON). Без LLM — эвристический план по признакам события и компании
   (есть ли данные банка о клиенте, есть ли сюжет, сколько изданий подтверждают, публичная ли компания).
   Обязательный минимум (факты, профиль, анализ влияния) добавляется, даже если модель его не запросила.
2. **Инструменты** (только из реестра, лишние аргументы отбрасываются): `get_event`, `get_company_profile`,
   `get_client_card` (данные банка), `analyze_impact` (правила), `search_bank_analytics` (RAG),
   `search_news` (сюжет и подтверждения), `get_market_reaction` (акции).
3. **Контекст.** Результаты шагов накапливаются в `Ctx.data`, источники — в `Ctx.sources` с id для ссылок.
4. **Самопроверка** (`agent_rules.py`):
   - полнота — есть ли факты, связь с компанией, позиция банка, подтверждения;
   - непротиворечивость — противоположные сигналы в новости, разные цифры в изданиях одного события, позиция банка
     против направления новости, оценка пользователя против оценки правил;
   - обоснованность — у каждого утверждения есть существующий источник; выводы модели без опоры на входные данные
     отбрасываются.

   Нет позиции банка — повторный поиск по теме и отрасли; одно издание или разные цифры — поиск других публикаций;
   банк расходится с новостью — поиск более свежего материала. До 2 раундов. Расхождения снижают уверенность на 10
   и показываются пользователю, чего не хватило — в `data_gaps`.
5. **Ответ** на 6 вопросов кейса; к «Что произошло?» — участники, сроки, подтверждённость; к «Действиям» — вопросы
   для анализа, что отслеживать, сценарии (вероятный по оценке банка помечен); вывод «с учётом аналитики банка».
   Уточняющий вопрос без LLM — подборка относящихся к нему утверждений, с LLM — ответ модели. Ответ проверяется
   Pydantic-схемой `AgentResultOut` (`GET /api/agent/schema`). Каждое утверждение — с типом (`fact` — из новости, `bank` — позиция банка,
   `client` — данные о компании, `ai` — вывод модели или правил) и ссылками на источники. С LLM модель переписывает
   черновик; утверждения «позиция банка» без ссылки на найденный фрагмент отбрасываются.

Трассировка (план, шаги, аргументы, итог, время) — в таблице `agent_runs`, в логе `alpha.agent` и в интерфейсе
(«Как агент пришёл к выводу»).

## Безопасность в архитектуре

```
 пользователь ──► FastAPI (/api) ──► агент ──► реестр инструментов (только чтение, проверка аргументов)
                     │                 │            ├─ данные клиента (обезличенные, том только для чтения)
                     │                 │            ├─ аналитика банка, новости (локальные данные)
                     │                 │            └─ правила, рынок
                     │                 └─► llm_client ──► белый список моделей ──► лимит токенов
                     │                                    └─ маскирование реквизитов ──► шлюз / свой сервер
                     └─► журнал: agent_runs, llm_calls, лог alpha.agent / alpha.llm
```

- Права: агент не может писать в базу, выполнять команды или ходить по произвольным адресам — таких инструментов
  нет. В продуктиве — вход через Альфа-Бизнес и роли (собственник, финдиректор, казначейство): доступ к карточке
  клиента с продуктами банка и платежами — только для ролей этого клиента; проверка — в API до вызова агента.
- Чувствительные данные: в модель уходит только контекст, собранный агентом (без платежей и идентификаторов физлиц),
  перед внешним шлюзом — маскирование; режим `local` — данные не покидают контур.
- Контроль: каждый шаг агента и вызов модели журналируются; модель вне списка кейса не вызывается; дневной лимит.

## Масштабирование и сопровождение

- **Новые отрасли** — отраслевой шаблон в `catalog.py` (продукты, клиенты, риски) и соответствие ОКВЭД → шаблон в
  `lookup.template_by_okved`; правила каналов влияния (`analysis.py`) общие для всех отраслей.
- **Новые клиенты** — данные в той же схеме CSV (`CLIENT_DATA_DIR`); профиль собирается автоматически.
  В продуктиве — витрина банка вместо CSV, тот же интерфейс `clients.card`.
- **Новые источники** — RSS в `sources.json` и реестр изданий `outlets.json` (репутация, холдинг); API банка —
  коннектор `AlfaBankSource`; аналитика банка — файлы в `BANK_DOCS_DIR`.
- **Новые инструменты агента** — функция и строка в реестре `agent.TOOLS`; планировщик-модель видит их автоматически.
- **Модели** — переменными `LLM_*` (шлюз, своя модель), без изменения кода.
- **Нагрузка** — анализ считается в фоне и хранится снимком на компанию; запросы читают готовое. Для многих
  пользователей: PostgreSQL вместо SQLite, очередь фоновых задач, отдельный сервер модели (vLLM).
- **Сопровождение** — тесты без сети (`pytest`), журнал вызовов модели и запусков агента, метрики качества
  (README «Мониторинг качества»), lock-файлы зависимостей, один образ Docker.
