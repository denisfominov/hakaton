# Задачи по потокам

Состояние на 2026-10-20. Задачи выведены из [GAP_ANALYSIS.md](GAP_ANALYSIS.md) (номера пробелов — «топ-10»),
форматы обмена — [CONTRACTS.md](CONTRACTS.md), процесс веток и PR — CLAUDE.md. Задачи в GitHub Issues не заводим:
этот файл и есть список.

**Шаг 0 (до старта потоков):** слить в `main` по порядку `agent-llm`, затем `ai-layer`. `ai-layer` основана на
`agent-llm`, которой ещё нет в `main`. Все ветки потоков — от свежего `main` после этого.

## Что изменили в схеме потоков и почему

Базовая схема: A — контекст компании и ранжирование, B — источники и RAG, C — агент и LLM, D — интерфейс и сдача.
Анализ пробелов показал четыре места, где она даёт сбой:

1. **Оценка качества — явно в поток A** (теперь «контекст, ранжирование и оценка качества»). Пробелы 3 и 9
   (разметки нет, мониторинга нет) — общие для всех, поэтому без владельца они бы потерялись. A лучше всех знает,
   что считать качеством отбора. D строит страницу мониторинга по данным A.
2. **Позиция банка — на стыке B и C с контрактом.** Пробел 2 (цитаты банка к не связанным новостям) нельзя
   закрыть в одном файле. B отвечает за выбор фрагментов (`bank_rag.py`: близость фрагмента к самому событию),
   C — за то, как агент их использует (`agent.py`: совпадение или расхождение только по общим сигналам).
   Формат фрагмента фиксируем в контрактах (`BankHit`, версия 1.1) в PR задачи B1.
3. **`main.py` делим на роутеры первым делом (D2).** Сейчас все потоки правят один файл на 1000+ строк — это
   главный источник конфликтов. После D2 у каждого потока свой роутер в `backend/app/api/`.
4. **Вход и роли разведены:** `entry.py` (токен, журнал входов, безопасность) — у D вместе с макетом и
   SECURITY.md; `roles.py` (как роль меняет ответ) — у C.

## Правила против конфликтов

1. **Свои папки и файлы** — по таблицам выше. Файл другого потока меняем только маленьким PR с ревью владельца.
2. **Общие файлы** — `config.py`, `schemas/api.py`, `pipeline.py` (общий для A и B), `db.py`, `requirements*`,
   `.env.example`, `Dockerfile`, `docker-compose.yml`, `main.py` до D2. Их меняем отдельными маленькими PR на одно
   изменение и сливаем быстро; без переформатирования и «заодно поправил».
3. **Перед PR:** `git checkout main && git pull`, влить `main` в свою ветку, прогнать
   `cd backend && python -m pytest -q` и `cd frontend && npm run build`.
4. **Одна задача — одна ветка** `<тип>/<поток>-<суть>` (например, `feature/b-bank-event-link`). Если задача
   зависит от неслитой ветки — написать это в описании PR.
5. **Документы потока** — в `docs/<поток>/` (`docs/a`, `docs/b`, `docs/c`, `docs/d`); общие документы правит
   владелец. README и CHANGELOG собирает D: каждый PR несёт в описании готовую строку для CHANGELOG и, если нужно,
   абзац для README.
6. **Контракты** меняются по правилам [CONTRACTS.md](CONTRACTS.md): новое необязательное поле — в своём PR с
   обновлением JSON-схем; несовместимое изменение — отдельный PR с повышением версии.
7. **Бюджет LLM:** платные вызовы пачками делает только C; остальные работают в мок-режиме
   (`LLM_PROVIDER=mock`) или с маленьким `DAILY_BUDGET_RUB`.
8. **Данные кейса, PDF, `.env`, веса моделей** не коммитим (CLAUDE.md); кэш `data/demo_cache` коммитит только C.
