«Как добавить задачу» ниже.

## Как читать

- **Основная таблица:** ID · формулировка (одной фразой) · что делается и где · для чего по ТЗ (пункт брифа) ·
  статус · кто · PR или ветка · дата слияния или начала. Размер, зависимости, цена в ₽ и проверка — во второй
  таблице «Детали задач», по тому же ID.
- **Пять статусов:** сделано · нужна доработка (начато, но не закончено) · не начата · временно отложена (в скобках —
  до какого пункта) · отброшена по ходу решения (причина — в «Что делается»).
- **Потоки (буква ID):** A — качество и контекст клиента · B — источники и поиск по аналитике банка · C — агент и
  модели · D — интерфейс и сдача · J — ежедневная платная очередь (Q1 — сборка очереди, E1–E3 — её эксперименты) ·
  S — служебные (процесс и документы).
- **Кто:** P1 — «агент и интерпретация» (в TASKS.md — Ч1), P2 — «данные, поиск и качество» (Ч2), оба, человек
  (разметка и другое, что делает только человек). Зоны файлов — docs/TASKS.md.
- **Родитель и дочерние:** большая задача делится на дочерние с номером через точку (C10 → C10.1, C10.2).
  Родитель остаётся строкой-заголовком: «сделано» — когда сделаны все дочерние, «не начата» — когда не начата ни
  одна, иначе «нужна доработка». ID никогда не переименовываются и не переиспользуются.

## Как добавить задачу (Intake)

**Откуда приходят задачи:**
1. Вы в окне Claude Code: «add task: <свободный текст>» — цель, ошибка или идея, одна строка или несколько.
2. Коллеги дописывают строку в конец [TASK_INBOX.md](TASK_INBOX.md): что и зачем (если известно), дата, кто
   написал. Только дописывать, новые — внизу.
3. Claude по находкам в своей работе: предлагает их в отчёте, в реестр они попадают при следующем обновлении.

**Порядок разбора** — по словам «add task …» или «process the inbox»:
1. Прочитать реестр коротко (поиск по ID и формулировкам) и входящие.
2. Найти дубли и пересечения. Если пересекается — расширить существующую строку и сказать об этом.
3. Выбрать букву по области: A качество и контекст, B источники и поиск по банку, C агент и модели, D интерфейс и
   сдача, J ежедневная платная очередь, S служебные. Номер — следующий свободный.
4. Самому вывести «Для чего по ТЗ». Спросить не больше двух вопросов — только если не ясен пункт брифа или объём;
   иначе записать допущение в строку.
5. Разбить по правилам ниже; поставить статус «не начата», владельца, зависимости, размер, цену.
6. Во входящих пометить строку как разобранную и дописать новые ID.
7. Показать новые строки простыми словами и предложить место в порядке работы: до или после каких открытых задач и
   почему.

**Где правится реестр:** только в docs PR из ветки `docs/register-<дата>`, никогда в PR задач. Разбор готовит эту
ветку, пушит её и даёт ссылку. Если вы поправили на GitHub ячейки статуса или формулировки, следующий разбор
сохраняет ваши правки и не перезаписывает их.

## Правила

1. **Строка — до работы.** Каждая новая задача получает строку до начала работы: «не начата», владелец. Без строки
   работу не начинаем.
2. **Одна задача — один PR, одно окно Claude, размер S или M, один владелец, одна проверка.** Больше (L) или в
   папках двух владельцев — делим на дочерние (C9 → C9.1, C9.2); родитель не переименовываем.
3. **Задача выросла по ходу работы** — остановиться, предложить деление, добавить дочерние строки. Тихо расширять
   объём нельзя.
4. **Описание PR начинается** со строки `Task: <ID> - <статус>`.
5. **PR задач реестр не правят.** Раз в день один docs PR (`docs/register-<дата>`) обновляет статусы по слитым PR с
   прошлого обновления (`git log --merges`) и разбирает входящие. Делает тот, кто координирует.
